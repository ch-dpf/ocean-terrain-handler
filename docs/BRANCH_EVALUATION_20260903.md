# main-zy 当前工作区与 main 地形切片评估

评估日期：2026-09-03。结论来自本机实测，业务代码未修改。

## 结论

当前工作区在去除 GDAL/Docker 运行依赖、预处理耗时、临时文件占用和 Geodetic 元数据方面有优势；但本次同存储测试中，**纯切片耗时约为 main 的 2.95–3.24 倍，预处理＋切片总耗时约为 1.36–1.91 倍**。不能据此认定当前分支性能优于 main。

普通瓦片内部，南极样例近似等价，海岸与海底样例存在米至数十米的局部差异；**海底数据边缘出现最高约 1,940 米的参考误差**。减少相邻瓦片裂缝不等于提高真实高程精度。当前工作区尚不宜作为已验证等价的 main 替代实现。

## 方法和公平性

1. 两分支读取相同的 Windows 源目录，只读挂载；中间数据和瓦片均写到同一个 Docker Linux 命名卷 `ocean-terrain-handler_workspace_data` 的独立目录。
2. 所有计时顺序执行，避免本次测试间的 CPU/I/O 竞争。每条分支三次独立输出，报告中位数；没有主动清理 OS 缓存，不是严格冷启动实验。主机其他已有服务没有停止。
3. Linux/WSL2；Docker 可见 28 个逻辑 CPU、约 39 GiB 内存。每个测试容器限制 4 CPU 配额，切片线程 4，缓存参数 512 MiB。当前预处理线程仍按实现的 `os.cpu_count()` 自动选择，4 CPU 是总配额，不代表仅创建四个线程。
4. Mesh / Geodetic / average，z10→z0，默认 tile size 65、mesh quality 1、error threshold 0.125，Cesium-friendly、顶点法线开启，resume 关闭。预处理：EPSG:4326、bilinear、fill_nodata、2/4/8/16 overviews、256 TIFF block。
5. 当前 Python 代码直接复制本次工作区；复用 worker 镜像已编译的 C++ 扩展，其七个随包原生源码文件与工作区逐文件一致，扩展 SHA256 已保存。
6. main 使用其真实 `preprocessor.py` 函数及 `build_ctb_command` 参数生成函数，通过 AST 加载避免服务依赖；以同步子进程适配进度包装器。GDAL 3.12.4 和 CTB 在基线容器内执行，移除外层 `docker run` 包装，**计时不包含容器启动、Celery 排队、Redis、发布和浏览器加载**。这是核心处理流水线比较，不是完整部署延迟比较。
7. main 切片调用不生成 layer.json，发布时 `ensure_layer_json` 补建。当前切片耗时包含生成该小文件；不可把 main 此阶段缺少文件解释为不可发布。

旧的 `data/jobs/_bench` 结果采用当前分支写 Linux 卷、main 写 Windows bind 的不同存储路径，且 GDAL 各阶段分别启动容器，因此本报告不沿用旧的速度倍数，也不将仅比较头部 min/max 视为网格准确度。

main 填充输出及复制保留了较大的文件；当前保持压缩并以重命名替代最终复制，所以明显节省磁盘。切片文件本身没有同等比例缩小，海底样例反而增加约 14.9%，顶点从 61,845 增至 82,769。

main 三个预处理结果与原始栅格同网格且逐有效像素差值为零。当前 `n0e0` 也逐像素一致，但 `s85e80` 从 6001×6000 变为 6002×6001，`s5e130` 从 6000×6000 变为 6001×6000。当前即使同 CRS 也重新计算像素数并调整像元尺寸；`grid_dimension` 的浮点 ceil 行为是值得定位的因素。两个不同网格没有强行用数组下标比较。

## 网格准确度

独立解码 gzip quantized-mesh，检查顶点量化值、三角形索引、边界索引和法线扩展长度。双方第一轮各 3,548 个文件均结构解码成功，坐标文件集合完全一致，均包含法线。

精度参考为**源 TIF 的双线性高程**，不是测量真值。对每个 z10 瓦片取归一化坐标 0.1/0.3/0.5/0.7/0.9 的 25 个点，以三角形重心插值恢复网格表面高程，只保留源数据有效且双方均可插值的共同点。每样例 20,164 个共同有效点。没有只比较两分支不同位置的顶点。平均重采样和 LOD 简化本来就会与原始点高程不同，以下 RMSE 不能全部归因于实现缺陷。

这些瓦片内部采样点未发现“源高程绝对值>100m而网格恰为0m”的情况，但该采样不能排除狭窄边缘过渡带。

### 共享根瓦片问题

两分支三个样例的两张 z0 根瓦片都在 horizon occlusion point 字段含 NaN/Inf，其余被检查结构可正常解码。共每分支6个文件。应单独验证 Cesium 剔除/加载行为；本次没有把静态解码成功宣称为浏览器完整渲染验收。

**Heightmap 深海不适用（共享问题）：** 本次源最低-7604m、最高778m，双方 Heightmap 解码范围却为-1000～12106.2m。编码 `(height+1000)*5` 写入 uint16，低于-1000m会回绕。不能因生成成功就认为海深正确；本库海底数据应使用Mesh，或增加明确的范围校验与产品提示。

**当前 Mercator 元数据问题：** 实测 bounds 为 `[14471533.80,-1118889.97,15028131.25,-557305.26]`（米）。本库 `scripts/preview/app.js` 把 layer.bounds 直接传给 `Cesium.Rectangle.fromDegrees`，构成明确单位不匹配。Mercator 文件生成通过不代表本库预览定位通过。应输出经纬度bounds或由预览页根据projection转换。

## 建议处理顺序

1. 先解决海底有效数据边缘的零值过渡策略，同时验证边缘参考误差和接缝误差，不能只以消除裂缝为通过标准。
2. 处理同CRS预处理后像素数改变、overview尺寸/坐标语义差异，稳定海岸与边缘重采样结果。
3. 修正Mercator bounds单位，并给Heightmap增加深海范围校验；检查共享根瓦片非有限字段。
4. 针对当前切片的采样、解压、相邻瓦片重复读取、fsync分别做性能剖析。保持实际持久化语义一致后再谈加速；本轮没有修改这些实现。
5. 扩展到真实NODATA孔洞、其他CRS、跨日期线、多个相邻TIF、z11以上及Cesium实际浏览器渲染，再决定是否替换main。

本次未设业务精度验收阈值，因此不给出“全面合格”的结论。按本轮样例，main 的核心切片速度和海底边缘参考准确度更稳；当前在磁盘占用、去外部依赖与Geodetic元数据方面更好。
